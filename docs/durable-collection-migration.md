# Переход фонового сбора на Durable Objects

17 октября 2026. Локальная версия backend `0.3.0`. Выпуск в production
и регистрация Durable Object ещё не выполнялись.

## Исполнение сбора

В существующий Worker добавлен SQLite-backed `CollectionRunner`, один
именованный объект `owner` на установку. Его хранилище содержит alarm,
счётчик выбора и число инфраструктурных повторов. Задания, OAuth, receipts,
снимки, ручные поля и checkpoints остаются в существующей D1.

Cron `*/5 * * * *` вызывает только `ensureAwake`. Объект сам продолжает
готовое задание через секунду после порции; будущий backoff или lease
определяет время ожидания. Включённые расписания дополнительно проверяются
раз в минуту для возрастных окон и свежести комментариев. Пауза ожидания
не держит обработчик активным. Конкретные сроки discovery/Stories/периодов
и сверки каталога сохранены.

Команды collection start, advance, control и configure выполняются внутри DO
через RPC. Ответы остаются синхронными; ошибки передаются как безопасные
данные и превращаются в прежние Problem Details с кодом и Retry-After.
GET остаётся чтением. Прямые публичные sync/refresh и разовые comments endpoints
сохраняют прежний контракт и исполняются в HTTP Worker; переход относится
к сохраняемым collection jobs и автоматическому расписанию.

Alarms и RPC сериализованы внутри объекта. D1 leases и проверки владельца
при записи сохраняются, в том числе для параллельного прямого sync и старой
версии Worker. Перед работой сохраняется recovery alarm; инфраструктурные
сбои получают явный повтор от пяти секунд до пяти минут. После исчерпания
шести platform retries объект не должен оставаться без будущего пробуждения.

## Удалённые ограничения и дублирование

- Убрана зависимость продолжения от следующего пяти минутного Cron.
  Пятиминутная задержка сохраняется для ошибок и recovery, где она является
  backoff, а не ограничителем полезной пропускной способности.
- Удалены `nextJob`, `workHeads` и выбор единственного `nextSchedule`.
  Все pending jobs и enabled schedules рассматривает один `selectWork`.
  Будущий срок alarm читается одним простым агрегатным запросом без повторного
  полного планирования и обхода истории.
- Чередование архивной работы и комментариев отвязано от времени суток и
  пятиминутных слотов. Счётчик выбора переживает перезапуск DO; архивный резерв
  вращается по последней попытке, срочная неархивная работа имеет приоритет.
- Комментарии используют 50 корневых элементов вместо 5. Сохранение делится
  по размеру JSON до 1,5 MB вместо групп по 25 записей. Старые операции
  продолжаются со своими сохранёнными параметрами.
- Удалён специальный обход runtime imports ради CPU Cron. Общие архитектурные
  проверки domain/application/presentation и публичных границ модулей сохранены.
- Убраны оценки перегрузки из предположения «три шага за 15 минут».
  `overload=not_measured`; прежние числовые оценки стали необязательными
  в OpenAPI и обновлённом MCP-контракте.
- `createScheduledOperations` заменён на `createCollectionExecutor` без
  отдельной ленивой обёртки reader. Одна область на порцию сохраняет бюджет
  и не удерживает расшифрованные credentials между вызовами.

Сохранены одна публикация в атомарной порции, максимум шесть HTTP attempts,
90 секунд wall deadline и резерв 15 секунд. Они ограничивают также запросы
к источнику и D1, а не только CPU. Для D1 Free документирован предел 50
запросов за вызов и 2 MB на строковое значение; увеличение CPU этого не
отменяет. Источник: [D1 limits](https://developers.cloudflare.com/d1/platform/limits/),
проверено 17 октября 2026.

Сохранены основные метрики до необязательных полей, группировка запросов
к Meta, object-scoped capability cache, quota/backoff и защита от повторной
страницы. Это обеспечивает полноту и честность данных. HTTP-router кешируется
и загружается по первому fetch: HTTP Worker и Cron по-прежнему имеют свои
ограничения Free.

## Локальная проверка

Root `pnpm check` прошёл: 167 backend-тестов в 15 файлах, 25 MCP-тестов,
проверки типов и границ, Worker dry-run и MCP build. Локальный список pending
D1 migrations пуст. Хеши изменённых файлов и исходного снимка сохранены в
[durable-collection-checks.json](durable-collection-checks.json).

Тесты используют настоящие локальные DO, SQLite и D1 с контролируемым
источником. Проверяются продолжение через alarm без Cron, потеря checkpoint
после snapshot commit, eviction с сохранённым alarm и счётчиком, повторное
пробуждение, отключение автоматического исполнения, сериализация ручного
advance с alarm и сохранение ошибок через HTTP/RPC. Стресс-случай комментариев
проверяет 2550 корней и ответов с крупным текстом и границы D1.

Перед изменениями сохранён локальный снимок рабочего дерева:
`/private/tmp/social-analytics-before-durable-objects-20261017`.
Он не содержит `.dev.vars` или `.env`. Прежние незакоммиченные изменения
сохранялись как исходная база; массового отката к Git HEAD не было.

Локальная эмуляция проверяет логику, но не доказывает тарифное CPU enforcement
или надёжность реального источника. После разрешённого выпуска необходимы
24–48 часов естественного выполнения и минимум два ежедневных цикла.

## Выпуск и откат

1. Выполнить root `pnpm check`, проверить pending D1 migrations и снять
   актуальный checkpoint production: версия, задания, cursors, leases,
   последние receipts и снимки. Не сбрасывать существующие задания.
2. После явного разрешения выпустить проверенный Worker с binding
   `COLLECTION_RUNNER` и migration `collection-runner-v1` с
   `new_sqlite_classes: ["CollectionRunner"]`. Это регистрация класса DO;
   отдельная аналитическая БД не создаётся. Платный тариф не подключается.
3. Проверить на фактическом Free alarm после завершения HTTP, реальный
   CPU-бюджет, прогресс прежних jobs без ручного advance, отсутствие дублей,
   квоты источника и D1, duration DO, freshness и пропущенные окна наблюдений.
   Успешные `/health` и alarm без новых данных не являются приёмкой.
4. Для отката сначала выпустить эту же версию с
   `COLLECTION_RUNNER_ENABLED=false`, дождаться завершения текущей порции
   и проверить остановку автоматических alarms. Затем вернуть предыдущую
   версию Worker. Не удалять namespace и не выполнять обратные миграции D1.
   Старый Cron продолжит сохранённые задания с их checkpoints и leases.
