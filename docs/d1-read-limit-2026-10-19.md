# Блокировка сборов по суточному лимиту D1

19 октября 2026, Asia/Yekaterinburg (диагностика с 00:15 местного времени).

## Текущее состояние

Production D1 вернула Cloudflare error 7500: `Your account has exceeded D1's
free tier daily row read limit`. Backend 0.3.3 и плагин отвечали общим 500.
Квота сбрасывается 19 октября в 05:00 по Екатеринбургу (00:00 UTC).
Исчерпанную квоту код не восстанавливает. Платный тариф не подключался.

Текущие staleSnapshots и частоту Stories надёжно прочитать не удалось.
Последний проверенный замер до блокировки: 18 октября 23:55 местного времени,
84 просроченных снимка из 242 публикаций; comments pass 142 страницы,
86 публикаций, 576 наблюдений. Эти числа не объявляются текущими.
Один маленький COUNT перед получением полного сообщения ошибки вернул
750 jobs; он не доказывает ни продвижение, ни отсутствие Story loops.
После подтверждения лимита диагностические обходы D1 прекращены.

повторные сканирования, а не большой объём возвращённых приложению данных.
LIMIT 100 не предотвращал полный поиск, когда подходящих строк не было.

## Исправления 0.3.4

- Ошибка лимита D1, включая обёртку Drizzle cause, возвращается как безопасный
  HTTP 503 / DATABASE_DAILY_LIMIT_REACHED с Retry-After до следующего 00:00 UTC
  и пятисекундным запасом. SQL, параметры и сообщения провайдера наружу не идут.
- CollectionRunner сохраняет databaseBlockedUntil в существующем runtime
  хранилище DO, не обращается к D1 во время известной паузы и оставляет alarm
  на время сброса. Cron не сокращает эту паузу; перезапуск DO её не теряет.
  После срока обычная очередь продолжается без сброса job IDs и cursors.
- Возрастные окна используют диапазон published_at для каждого из семи
  targets через существующий media_account_published, вместо обхода всех
  публикаций для каждого target. Границы окна и семантика снимков сохранены.
- Подготовлены четыре индекса в двух миграциях: requested_at для retention,
  частичный requested_at только для непустых sample, account/requested_at/id
  для последнего receipt, account/observed_at для account insights.
  Частичный индекс важен: уже очищенные старые строки не должны повторно
  попадать в поиск sample. Новых таблиц и хранилищ нет.

Миграции [0013](../backend/migrations/0013_opposite_wendell_vaughn.sql) и
[0014](../backend/migrations/0014_colossal_gargoyle.sql) применены локально.
Они содержат только CREATE INDEX. Удалённо пока не применены. Владелец явно разрешил обе миграции после
сброса квоты; применение включено в продолжение восстановления на 05:05. Выпущенный backend совместим с прежней схемой;
полная экономия сканирований требует установки этих индексов в production.

## Проверки и выпуск

Root pnpm check прошёл: 186 backend-тестов, 27 MCP-тестов, типы, границы,
format, OpenAPI contract check, dry-run backend и сборка MCP. Node 24.18.0,
pnpm 11.15.1. Регрессии проверяют read/write quota, безопасный 503, сохранение
паузы при eviction и выход из неё после UTC reset; EXPLAIN проверяет четыре
индекса и индексный диапазон опубликованных дат. Поведение после reset
проверено локально, не выдаётся за уже состоявшееся production-восстановление.

Backend 0.3.4, source e449d96, выпущен в существующий Worker 19 октября
в 00:25:59 по Екатеринбургу (18 октября 19:25:59 UTC). Version:
e828ef32-6c65-43b9-86c0-3706420c4c38, deployment:
47383ee7-ffc4-4f95-be47-3f8fcb539a6a, 100% traffic. Скачанный bundle совпал с
проверенным SHA256 b8546108dabea6e44665aac81b756ada15b3e6f112b6056d5936d51a4933bf2b.
Прежние D1, DO namespace/class, secrets bindings, Cron и выключенные logs
сохранены. Production GET и установленный MCP теперь явно сообщают
DATABASE_DAILY_LIMIT_REACHED / 503. Плагин 0.4.1 не менялся.

Сборы пока заблокированы внешней квотой. Повторная проверка после 05:00 должна
подтвердить реальное продвижение по receipts, новым полезным snapshots,
сохранённым job counters и интервалам Stories. Успешный health этого не
подтверждает. История, задания и курсоры этой работой не удалялись и не сбрасывались.
