# Полнота и стоимость сбора API — 2026-10-08

Отчёт фиксирует исходное состояние до доработок 2026-10-08.
Реализованные исправления и итог проверки — [collection-improvements.md](collection-improvements.md).
В исходном состоянии все доступные данные не собирались. Основные метрики Reels покрыты хорошо,
но есть пробелы в полях, периодной истории и гарантиях своевременного наблюдения.
Алгоритм комментариев уже существенно оптимизирован; главные оставшиеся затраты —
повторное определение неподдерживаемых полей и отдельные запросы Account Insights.

документация Meta. Исходное состояние — commit `8ed0040`, опубликованные версии
backend `0.2.12` и MCP `0.3.5`. Реальное состояние прочитано разрешёнными GET
через backend в `2026-10-08T04:34:30.235Z`: очередь, агрегаты покрытия, границы
периодов и история профиля. Каталог публикаций, тексты и секреты не выводились.
Полный новый обход Meta в рамках аудита не запускался.

Это проверка интеграции Instagram API with Instagram Login v26.0.
Остальные социальные сети ещё не подключены. Документация Meta местами содержит
примеры v25.0 и противоречивые пометки доступности; документированное поле не
считается доказанно возвращаемым для конкретного аккаунта. Его отказ должен

[Media Insights](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media/insights)
и [Account Insights](https://developers.facebook.com/documentation/instagram-platform/api-reference/instagram-user/insights).
Список запроса не гарантирует наличие значения: возраст, аудитория, разрешения
и особенности аккаунта могут ограничить ответ.

Состав полей комментария подтверждён
[IG Comment](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-comment),
метаданных — [IG Media](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media),
упоминаний — [Mentions with Instagram Login](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/mentions).
Длительность ролика в обычном читаемом Media contract не документирована;
ручная длительность с source=manual остаётся обоснованной.

Не следует добавлять поля другого режима входа. По
[Meta changelog](https://developers.facebook.com/documentation/instagram-platform/changelog)
story link_clicks доступен только с Facebook Login; новые media reposts_count,
saved_count/shares_count, агрегированные media-метрики paid+organic и collaborators также имеют
ограничения Facebook Login. Их отсутствие в текущем адаптере не является ошибкой.
Напротив, расширение facebook_views на Feed/Stories отражено в changelog
от 2026-04-22 и учтено локальным исправлением.

Account Insights при этом сохраняют собственные определения Meta: reach,
accounts_engaged и total_interactions могут включать рекламу. Их нельзя
объявлять organic-итогом всех публикаций или подменять суммой media insights.
Это ограничение уточнено в [metrics.md](metrics.md).

## Риски полноты исходного состояния

1. **Ранние снимки публикации не гарантированы.** Production обнаруживает новые
   объекты раз в шесть часов, а окно первой контрольной точки заканчивается
   в возрасте 1,5 часа. Узнать объект через шесть часов и восстановить его
   одночасовую статистику невозможно. Новый default=60 минут снижает риск,
   но не меняет существующую настройку и не гарантирует срок при большой очереди.
   Нужны частый discovery и измерение фактической задержки/пропущенных окон.
   Код: `collection/domain/age-policy.ts`, `collection/application/collect.ts`.

2. **Автоматическая периодная история неполная.** Cron раз в сутки сохраняет
   total_value последних трёх полных UTC дней. Дневные значения, точные недели
   и месяцы автоматически не фиксируются. В production есть вручную сохранённые
   24/48/168-часовые интервалы; это не сплошная автоматическая история.
   Перекрывающиеся трёхдневные итоги не дают уникальный недельный reach и не
   служат надёжным способом восстановления отдельных дней. Нужны устойчивые
   дневные интервалы, точные недельные/месячные итоги и повторное чтение периода
   после задержки Meta. При лимите 31 день месяцы можно сохранять отдельно.
   User metrics доступны ограниченное время — [правила Insights](https://developers.facebook.com/documentation/instagram-platform/insights).
   Код: `app/create-features.ts`, `account-insights/index.ts`.

3. **Исчерпание пагинации не доказывает наличие всех replies.** В синтетическом
   ответе omitted replies увеличивает omittedBranches, но отдельный запрос к
   этой ветке не делается и checkpoint помечается complete. Ограничение видно
   в API публикации; сводный partial=0 может скрывать этот смысл. Нужен отдельный
   показатель непроверенных веток и ограниченный fallback для omitted, без
   возврата к запросу replies для каждого пустого родителя. Реальную потерю
   конкретных replies этот аудит не установил. Meta также может не отдавать
   часть текстов при наличии числового счётчика; известный пример уже описан
   в [data-collection-fixes.md](data-collection-fixes.md).
   Код: `collection/application/bulk-comments.ts`.

4. **Недоступный старый объект может блокировать продолжение прохода.** Нет
   классификации окончательно удалённого/недоступного media с сохранением
   причины и переходом к следующему объекту. Ошибка повторяется с backoff,
   после пяти сбоев отдельное задание требует resume. Пропускать объект можно
   только при подтверждённой окончательной недоступности; auth/rate limit
   нельзя превращать в «удалён». Код: `collection/application/collect.ts`.

5. **Discovery прекращается на первом знакомом объекте.** Это экономит запросы,
   но предполагает стабильный порядок выдачи и появление нового объекта в её
   начале. Более старый добавленный объект либо изменения ниже границы останутся
   незамеченными до полного обхода. Нужен редкий полный пересмотр каталога,
   отдельно от полного прохода комментариев по уже сохранённому каталогу.

Для Stories ограничение особенно жёсткое: активный объект и его insights имеют
короткое окно, а Insights webhook для Instagram Login не поддерживается.
Перебой polling не компенсируется существующим webhook комментариев.
Сервис также не получает метрики отдельных детей карусели и рекламные тексты
комментариев как обычные organic comments. Эти ограничения описаны в
[Media Insights](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media/insights)
и [Media Comments](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-media/comments).

## Оптимальность алгоритмов

| Участок | Оценка и действие |
| --- | --- |
| Комментарии | Удачный базовый алгоритм: cursor pagination, replies expansion, продолжение частичных веток, дедупликация, атомарные lease/checkpoint, bulk INSERT. Нет запроса к каждому пустому родителю. Сложность зависит от числа страниц и продолжений; объём одной страницы ограничен. |
| Возрастные точки против периодических задач | Раньше age имел безусловный приоритет. В воспроизведении 12 готовых age-операций дали 12 refresh и ни одной Stories/discovery/Insights операции. Исправлено сравнение сроков; новые тесты обслуживают discovery и Stories при незавершённом age backlog. Это выбор очереди, не гарантия срока завершения job. |
| Восстановление расписания | Раньше nextSchedule исключал failures>=5 при enabled=true: шестой запрос не выполнялся даже после backoff. Исправлено: повтор после retryAt, ограничение отдельного job сохранено. В production этого сбоя при чтении не было. |
| Account Insights | Было 11 последовательных insights-запросов плюс проверка профиля, теперь 12 плюс профиль из-за reposts. Следующая оптимизация — объединить 11 совместимых total_value полей, отдельно follows_and_unfollows/follow_type: в обычном успешном случае 3 внешних запроса вместо 13. Нужен транспорт для нескольких structured metrics и сохранение индивидуальных причин отказа. |
| Демография | Каждая из четырёх dimensions читает follower и engaged отдельно. Два совместимых поля можно объединить с одинаковыми timeframe/breakdown, сохранив раздельный результат и пороги аудитории. |
| Неподдерживаемые метрики медиа | Уже есть общий запрос и адресный fallback. Однако его результат забывается между объектами. Ошибки reposts и двух Facebook fields воспроизвели 5 insights-запросов на Reels, плюс профиль/каталог — 7, вместо 3 в успешном случае. Нужен кеш доказанных возможностей с областью account/version/product, TTL и повторной проверкой; нельзя кешировать всякий локальный not_supported как запрет для всех объектов. |
| Stories | Было 3 запроса insights на Story; replies объединены с основными полями, осталось 2: общий и navigation. Для страницы из пяти объектов обычный путь сокращён с 17 внешних запросов до 12, включая профиль и каталог. Неподдерживаемые поля могут потребовать дополнительных запросов fallback. |
| Lifetime selection в D1 | MAX/GROUP BY просматривал всю media_snapshots, включая остальные аккаунты. Исправлено на поиск последнего наблюдения каждой публикации аккаунта по snapshots_media_time. Новый индекс и миграция не требуются. |
| История операций в D1 | sawKnownMedia фильтрует ID через substr без отдельного operation index; repeatedPage ищет fingerprint в JSON. При росте истории это кандидаты для проверки планов и индексов. Пока изменения схемы не вносились. |
| API-квота | Клиент реагирует на rate limit через backoff, но не учитывает quota headers и Retry-After. Нужны адаптивное ограничение запросов и наблюдение фактического расхода. runBudget=1 ограничивает операции Cron, а не HTTP-запросы внутри них. |

Один глобальный шаг за пять минут даёт максимум 288 шагов в сутки на все
аккаунты. Даже 236 публикаций с одной страницей комментариев требуют минимум
19 ч 40 мин выделенного Cron; replies, расписание, audience, ошибки и другие
аккаунты увеличивают срок. Политика приоритетов не увеличивает пропускную
способность. PageSize=1 выбран для ограниченного шага; увеличивать его или
бюджет следует после проверки реального числа запросов/CPU и ограничений D1,
с сохранившимися lease и возможность продолжения. Дополнительная инфраструктура
для перечисленных оптимизаций не требуется.

Для SQL проверен EXPLAIN QUERY PLAN и совпадение выбора на синтетическом
SQLite-наборе: 50 аккаунтов, 1 000 media, 100 000 snapshots, три времени отбора.
До исправления план содержит SCAN всей snapshots_media_time и MATERIALIZE;
после — SEARCH media по account и SEARCH последнего snapshot по media_id.
Остаётся сортировка публикаций выбранного аккаунта. При M публикациях аккаунта
и S общих снимках затраты переходят от обхода S к M индексным поискам и
сортировке M. Это подтверждение структуры запроса, не замер production CPU.

## Проверки первого этапа аудита и выбранный приоритет

Регрессионные тесты охватывают разделение insufficient_audience/permission,
новые поля Stories, сохранение настоящего navigation total при неполной сумме
категорий, совместимость account metrics и восстановление расписания после
пяти ошибок. Проверены один шаг за запуск, Stories/discovery при age backlog,
идемпотентное продолжение, активные lease, старые курсоры и конкурирующие задания.
Root `pnpm check` проходит: 97 backend и 18 MCP/UI тестов, проверка типов,
форматирования, границ модулей и сборка без публикации. Контракт OpenAPI/MCP
перегенерирован; чтение новых разбивок в MCP и диагностический скрипт согласованы
с набором поддерживаемых сочетаний. Новые поля не проверялись живым сбором на
аккаунте владельца: для них подтверждены документация и локальные фикстуры.

Приоритет дальнейшей работы: сначала автоматическая точная периодная история
и фактическая задержка discovery, затем coverage omitted replies и продолжение
после окончательно недоступных объектов. После этого — batching Account Insights,
кеш возможностей и адаптация к квоте. profile_activity и расширенные метаданные
нужно добавлять вместе с подходящим контрактом хранения, источником и временем
сбора. Ни одно из этих незавершённых направлений не следует выдавать за полное
покрытие всех данных API.
