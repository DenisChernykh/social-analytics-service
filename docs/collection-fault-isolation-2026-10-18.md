# Изоляция ошибок сбора: backend 0.3.3 / MCP 0.4.1

18 октября 2026, Asia/Yekaterinburg. После прямого разрешения владельца
исправления отправлены в main, backend и частный плагин выпущены.
Старое задание возобновлено с сохранённой страницы 210 и завершено на 238-й.
Производственные результаты и ограничения проверки приведены ниже;
машиночитаемые доказательства — [production evidence](collection-fault-isolation-production-evidence.json).

## Исправленные причины

Архивный refresh выбирал публикацию с самым старым снимком. Отказ insights
одной карусели 2019 года (`100/2108006`) оставлял этот снимок самым старым
и переводил расписание аккаунта в общий backoff. Следующая попытка снова
выбирала тот же объект. Возраст публикации сам по себе не считается причиной
отказа и не используется для исключения старых постов.

Теперь отказ core insights отдельного объекта сохраняет доступные значения
из текущего ответа каталога и оставляет остальные поля `null` с причиной
`source_error`, `object_unavailable`, `invalid_request` или
`invalid_breakdown`. Receipt не подменяется старым наблюдением. Необязательные
запросы после такого отказа не расходуют остаток порции. Неполнота отражается
в `coverageState`; завершение операции не означает полноту всех метрик.

Отложенный повтор хранится в существующих `media.unavailable_until` /
`unavailable_code`: 5 минут для source error, час для invalid request /
breakdown, сутки для object unavailable. Источник может потребовать более
долгую паузу через Retry-After. Это временная отсрочка, а не утверждение об
удалении поста или неподдерживаемости поля. После её окончания объект снова
попадает в выборку даже при свежем частичном снимке.

Если ошибка возникла при чтении метаданных refresh, откладывается этот же
объект, а следующая порция аккаунта разрешается через секунду. Ошибки доступа
ко всему аккаунту, rate limit, транспортные ошибки и сбои сохранения сохраняют
прежнюю обработку. Схема D1 и миграции не менялись.

Stories могли получить завершённую sync-страницу, чей `nextCursor` совпадал
с входным. Повтор той же операции затем возвращал сохранённый результат
без нового HTTP запроса и увеличивал failures. Теперь collection pass сразу
становится `failed` с `INSTAGRAM_PAGINATION_STALLED` и отображается как
`effectiveState=incomplete`. Снимки и курсор сохраняются; следующий плановый
проход может начать новое обнаружение доступных Stories. Это не восстановление
истёкших Stories. Прежние ограниченные повторы комментариев сохранены.

## Продолжение сохранённого задания

Внутренний collection executor может повторить legacy sync-операцию с
`INSTAGRAM_SOURCE_ERROR` под тем же operation ID и с теми же параметрами.
Публичный API не принимает этот внутренний флаг: обычный replay terminal
failure по-прежнему не повторяет запрос источнику. Завершённые операции
по-прежнему возвращаются без повторного сбора. D1 leases, fencing и атомарное
сохранение не менялись.

В 18:19:26 UTC через установленный плагин выполнен один resume прежнего
ручного прохода `244da4fa-13c7-40fb-b48c-8988eeb3f21a`. Сохранены ID, 210
страниц и тот же checkpoint (125 байт; в доказательствах только SHA256).
Без ручных advance alarms прошли до страницы 238; в 18:21:05 UTC задание
завершилось с failures=0, errorCode=null, cursor=null. Старые failed Stories
не возобновлялись массово и не объявляются восстановленными.

## Статус и MCP

Добавлен `mediaRefresh`: `publications`, `missingSnapshots`, `staleSnapshots`,
`ready`, `deferred`, `retries` с кодами и сроками. Отсутствующий снимок,
устаревший снимок и временная отсрочка имеют разную семантику. Устаревание
считается по возрастной частоте публикации: час / 6 часов / сутки / неделя;
свежий частичный снимок не означает полноту метрик.

`effectiveState` / `waitingReason` различают ready, running, waiting,
lease_expired, incomplete и terminal states. Существующие `status` и cursors
сохранены. Новые поля контракта необязательны для совместимости.

OpenAPI локально переснят из backend, валидаторы MCP сгенерированы из него.
Корневая `pnpm check` теперь сначала сравнивает сохранённый OpenAPI с исходным
backend без сетевых обращений. Отдельная проверка пакета MCP не требует
исходников backend, поэтому сохраняется экспорт плагина на private Sites.
Плагин 0.4.1 опубликован как Sites 15, manifest и MCP server имеют одну версию.
Чтения статуса и завершённого задания через установленный плагин прошли
с новыми mediaRefresh и effectiveState.

## Проверка

Корневая `pnpm check` прошла: 179 backend-тестов в 16 файлах, 27 MCP-тестов,
проверки типов, форматирования, границ модулей и соответствия OpenAPI,
Worker deploy dry-run и сборка MCP. Единственное информационное замечание
Biome относится к прежней конкатенации строки в `export-sites.mjs`; ошибок
проверок нет. Node 24.18.0, pnpm 11.15.1. Миграций для этого исправления нет.

Регрессионные сценарии находятся в
`backend/test/collection-fault-isolation.spec.ts`: продолжение после отказа
insights, изоляция отказа metadata, сохранение account-wide auth/rate backoff,
повтор per-field ошибки, восстановление страницы 210 и новый проход после
зацикленного Stories cursor. Дополнительный тест сначала воспроизвёл replay
частичного completed refresh из-за 15-минутного окна operation ID при
5-минутном source cooldown. В 0.3.2 новые refresh ID используют 5-минутное
окно; сохранённые операции не переписаны. Тест прошёл после исправления.
Сценарии используют локальные D1 и runtime.

`collection-phase1.spec.ts` дополнительно проверяет настоящий путь
MetaClient -> HTTP 400 / Graph 100/2108006 -> receipt -> частичный снимок
с синтетическим источником. MCP-тест проверяет прохождение статуса без старых
оценок Cron capacity и сохранение новых счётчиков и признака incomplete.

## Дополнение 0.3.3: ограничение срочных Stories

Наблюдение выявило ещё один цикл: финальный снимок считался достаточным за
15 минут до истечения, но срочный поиск запускался уже за 20 минут. Кроме
того, API не возвращал нужную истекающую Story, хотя возвращал более новую;
старый снимок целевого объекта оставался просроченным. После остановки
повторяющегося cursor планировщик создавал следующий проход каждые несколько
секунд. К 18:44:27 было 26 таких новых заданий, история сохранена.

В 0.3.3 окно запуска и достаточности снимка согласованы (15 минут), а новые
срочные проходы допускаются не чаще чем через 5 минут после последней попытки
Stories. Пропуск объекта остаётся пропуском: попытка поиска не заменяет его
снимок. Тест с 18 минутами до истечения сначала воспроизвёл ранний запуск;
после исправления он проходит. Отдельная регрессия проверяет отсутствие
повторных проходов при пропущенном объекте и разрешение повтора через 5 минут.

24–48-часовая приёмка и два ежедневных цикла остаются открытыми. DO periodic
samples 0.3.2 не содержат CPU/memory/fatal errors, но telemetry неполна:
ранние invocation/Cron datasets были пусты; последующая выборка подтвердила
98 alarms и 2 RPC версии 0.3.2 с status=success. Ранние запросы ограничивались
бюджетом GraphQL.
Пустой ответ не трактуется как ноль ошибок. Суточный агрегат duration на
18:35 UTC — 288,15 GB-s; исчерпание duration этим чтением не подтверждено.
Текущие исходные отказы
Meta у 28 публикаций изолированы, но сами недоступные insights не восстановлены.

HTTP-версия не доказывает версию alarm: после deploy 0.3.3 телеметрия
ещё показывала alarms версии 0.3.2. Выпуски Worker и DO распространяются
с eventual consistency, что описано в [Cloudflare lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/).
Окончательная проверка ограничения повторов требует наблюдения реального
DO, а не только health, SQL кандидата или скачанного bundle.
