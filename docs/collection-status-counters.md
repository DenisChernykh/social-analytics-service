# Готовые счётчики состояния сборщика

23 октября 2026 по явному разрешению владельца применена production-миграция
`0016_great_firedrake.sql` и опубликован backend 0.3.12, source `c5900d2`.
Worker version `6c266fe6-2608-4900-b07c-fee9c5a972c3` получает 100% traffic
с 08:57:35 UTC. HTTP catch-up выполнен после переключения и завершения
старых активных операций. Контракт API/MCP совместим с текущим MCP 0.4.3;
отдельная публикация MCP для этого изменения не требуется.

Статус читает сохранённые итоги и текущее состояние публикаций. Он больше не
группирует историю снимков, receipts и завершённых периодов активности при
каждом запросе. История остаётся источником аналитических отчётов.

## Что хранится

- `media.collection_status_json`: последний снимок и его операция, наличие
  отложенных метрик, время последнего полезного значения, число снимков с
  неизвестным provenance, первые полезные наблюдения reach в семи возрастных окнах.
- `accounts.collection_jobs_json`: готовые итоги терминальных заданий по
  дню создания, origin и status. Активные задания читаются отдельно с их
  текущими сроками. Старый cursor сохраняет cutoff; если после него появились
  задания в том же дне, пересчитывается только этот пограничный день.
- `accounts.activity_periods_json`: последнее подходящее наблюдение периода
  активности с разделением API version/timeZone/from/to. Набор метрик и
  `request_deferred` проверяются при сохранении, а не на каждом чтении плана.
- `comment_media_state.unique_saved`: число уникальных ID комментариев.
  Повторное наблюдение/UPSERT не увеличивает число.
- `instagram_api_state.object_freshness_json`: последние попытка и успешная
  проверка каждого объекта. Они обновляются в существующих SQL-записях учёта
  HTTP, без дополнительного write на запрос. Удаление старых receipts не
  стирает сохранённое время последней проверки.

SQLite triggers поддерживают снимки, итоги заданий, периоды и комментарии
в транзакции исходной записи. INSERT с проигранной lease/fence и повторный
`ON CONFLICT DO NOTHING` не меняют счётчики. UPDATE/DELETE исправляют
производные значения; для редкой коррекции снимка пересчитывается история
только затронутой публикации. Изменение published_at пересчитывает её окна.
При одинаковом observed_at сохраняется прежний выбор последнего снимка по
порядку SQLite rowid. Новые частичные индексы ограничивают диагностику
активными попытками; остаточные leases терминальных заданий не теряются.

Сроки повторов, просрочки, возраст данных и открытые окна вычисляются от
текущего времени при чтении. Ответ не является замороженным кешем с TTL.
Счётчики аккаунта не выдаются в публичном account API. Новых облачных ресурсов,
базы аналитики или вызовов Instagram не добавлено.

## Проверка и измерение

Root `pnpm check` прошёл: 225 backend и 28 MCP тестов. Проверены повторы,
равные/out-of-order timestamps, неизвестные метрики с реальным нулём,
исправления и удаления, откат транзакции, старый cursor и смена суток,
возобновление заданий, разделение аккаунтов, таймеры без записи в базу,
недостаточные/отложенные наборы метрик и API/timeZone.
Миграция применена локально; `pnpm db:generate` не находит дальнейших изменений.

Воспроизводимый benchmark использует изолированную локальную D1/workerd и
исторический код commit `52b8be296d4fbe803f0045778187d8b2002477e4`.
База сначала создаётся до 0016, заполняется синтетическими данными, затем
применяется 0016. Старый и новый расчёты дают одинаковое состояние.

На 250 публикациях, 7 500 снимках, 7 500 receipts, 1 200 заданиях,
1 600 наблюдениях активности и 3 000 комментариев:

| Сценарий | До | После |
| --- | ---: | ---: |
| Основные SQL-компоненты статуса, rows_read | 125 877 | 2 798 |
| Чтение статуса, rows_written | 0 | 0 |
| Один HTTP begin/finish, rows_written | 9 | 9 |
| Новый снимок + период + терминальное задание + уникальный комментарий, rows_written | 16 | 21 |

В замере включены все компоненты `D1Collection`, план периодов и API quota
state; одинаковые проверки аккаунта/расписания HTTP-обвязки не учитываются.
Снижение чтений в этой фикстуре — 97,78%, а не измеренная суточная экономия
production. Поддержание счётчиков требует дополнительной записи при изменении
аналитических данных; чтения не выполняют writes.

После добавления тестовых записей удвоение истории снимков сохраняет
2 799 reads против 2 799. Первичная миграция в этой фикстуре требует
51 118 reads и 1 984 writes. Это разовая стоимость заполнения/индексов.
Полные результаты: [benchmark JSON](collection-status-counters-benchmark-2026-10-23.json).

Повторить из корня workspace:

```sh
node backend/scripts/benchmark-status-counters.mjs /private/tmp/social-analytics-status-counters-benchmark.json
```

## Проверка production

В одном read-only сравнении на production старые компоненты статуса прочитали
71 140 строк, новые — 5 493 (−92,28%), writes — 0. Сравнивались все компоненты
D1Collection, наблюдения периодов и API quota state при одном времени расчёта;
одинаковая HTTP-обвязка account/schedule не включена. Ответы полностью совпали.
Это точечный замер, суточная экономия всей D1 ещё не измерена.

Проверены текущие производные значения по исходным данным, HTTP/MCP, bundle,
12 исторических снимков и конфигурация расписания. Результаты и нативные
rows_read каждого запроса: [production evidence](collection-status-counters-production-2026-10-23.json).

## Порядок выпуска

Выполнено по явному разрешению владельца на миграцию, публикацию и push:

1. Применить 0016 к существующей D1 с профилем `social-analytics`.
   Все обслуживающие triggers создаются до начального заполнения. Исходные
   снимки, комментарии, задания и расписание сохраняются.
2. Опубликовать backend 0.3.12. Дождаться завершения старых активных операций.
3. Выполнить `backend/scripts/status-counters-http-catchup.sql` на той же D1:
   старый Worker в промежутке между миграцией и переключением ещё мог записать
   receipts без нового поля HTTP-свежести. Скрипт объединяет максимумы и не
   откатывает уже сохранённое время даже после retention receipts.
4. Проверить `/health`, публичный статус/MCP, совпадение bundle, индексы,
   счётчики со стабильными исходными данными и неизменность контрольных снимков.
   Измерить реальные reads на production отдельно от локального benchmark.

Backend-код до 0.3.12 совместим с добавленными полями и triggers, поэтому при
откате Worker удалять счётчики/историю не требуется. Перед повторным включением
0.3.12 после старого кода нужно повторить HTTP catch-up.

SQL triggers и catch-up воспроизводятся генератором
`backend/scripts/status-counters-sql.mjs`; `pnpm check` проверяет совпадение.
После production-применения 0016 неизменна. Новая политика возрастных окон или
состава автоматических метрик потребует отдельной миграции пересчёта.
