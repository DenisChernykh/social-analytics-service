# Исправления сбора и доступности данных

Проверка 2026-10-03, официальный Instagram Login API v26.0, подключённый аккаунт
владельца. Секреты использовались только в памяти; исходные тексты комментариев
и OAuth-данные в диагностический вывод не включались.

## Вовлечённая аудитория

Одинаковые запросы country с `period=lifetime`, `metric_type=total_value`:
`last_30_days` вернул HTTP 200 и 0 категорий, `this_month` — HTTP 200 и 45 категорий.
Это воспроизводит причину прежнего пустого результата. Meta удалил старые окна
для engaged/reached demographics в v20.0; follower demographics имели другие
правила и поэтому прежняя загрузка сохраняла только категории подписчиков.

Сбор принимает this_month/this_week, чтение сохраняет прежние follower-окна.
this_week в проверке вернул Meta code 3006, Not enough users; это явно
недостаточная аудитория источника. Теперь сохраняется insufficient_audience,
без выдуманного нуля или общей ошибки доступности API.

Демография автоматически обновляется отдельным заданием по четырём разбивкам
после первичного каталога и при ежедневном обновлении активности.

Источники: [Instagram User Insights](https://developers.facebook.com/documentation/instagram-platform/api-reference/instagram-user/insights),
[изменение v20.0](https://developers.facebook.com/documentation/instagram-platform/changelog#may-21--2024).

## Комментарии

В проверке подтверждены выданный manage_comments и совпадение владельца media
с Instagram-scoped ID токена. Canonical user_id и scoped id отличаются; это
не означает, что публикации принадлежат другому владельцу.

Для публикации с текущим comments_count=270 прочитаны все шесть страниц limit=50.
Каждая страница вернула HTTP 200, data=[]; шестая действительно закончила
пагинацию. Повтор с default fields и fields=id даёт тот же результат. Другие
публикации с ненулевыми счётчиками тоже возвращали пустые страницы. Парсер
не отбрасывает тексты: их не было в исходном ответе Meta.
Полный повтор с передачей токена в query вместо Authorization, обоими способами
одновременно и с API v25.0 также вернул шесть пустых страниц. Способ
авторизации и переход с v25 на v26 это расхождение не объясняют.

До исправления в собственном кабинете Meta приложение было отмечено «Не опубликовано».
[Официальные правила режимов](https://developers.facebook.com/docs/development/build-and-test/app-modes/)
ограничивают функции разработки пользователями с ролями приложения.
После явного согласия владельца приложение переведено в Live. Подготовленные
URL политики и инструкций удаления сохранены в том же приложении; прежний
контактный email уже был правильным и не менялся. Кабинет подтвердил
«Ваше приложение опубликовано» и статус «Опубликовано».

Повтор 2026-10-03 08:00 UTC тем же подключением, `fields=id,text,timestamp`,
`limit=50`, к той же публикации вернул 50/50/50/50/50/20 текстов — всего 270,
comments_count=270. Последняя страница закончила пагинацию. OAuth не выполнялся
повторно и код чтения не менялся. Причина прежних пустых ответов связана с
неопубликованным режимом Meta; переход в Live восстановил чтение.

Отдельный проверочный сбор нескольких страниц заменён сохраняемым проходом
всего аккаунта с ответами на комментарии. Он не останавливается на пустой
промежуточной странице, поддерживает lease, retry/backoff, отмену и продолжение.
GET /comments по-прежнему возвращает только сохранённые тексты и честное покрытие.

## История профиля

Ранее endpoint и UI возвращали только последние 100 наблюдений без продолжения.
Записи в D1 не удалялись. Теперь endpoint имеет from/to и устойчивый nextCursor,
сортирует равные времена по ID и привязывает курсор к аккаунту и фильтрам.
Общий count, границы и net change относятся ко всему выбранному диапазону.
Карточка читает этот count и начало сохранённой истории независимо от первой
страницы. Загрузка карточки остаётся чтением и не запускает сбор.

## Полные аналитические выборки

В рейтингах и lifetime benchmark тоже оставался самостоятельный предел
первых 100 публикаций. Удалён: анализ проходит все страницы сохранённого
каталога с выбранными фильтрами; медианы и частота относятся ко всей выборке.
Сводка также исчерпывает пагинацию вместо прежнего предела 1000. Эксперименты
и разборы получают все сохранённые снимки публикации, а не последние 100.
Размер страницы 100 остаётся способом передачи данных, а не потолком выборки.

Постоянное расписание включено и теперь запускает также отдельные
возобновляемые задания демографии и полного сбора комментариев.

## Продолжение диагностики источника

Backend 0.2.6 опубликован, Worker version
`a77d048f-b21b-40c2-b4a3-c2fb5c9d7d6e`, commit `8cf14a3`.
Для конфигурации существующего приложения Meta доступны публичные текстовые
страницы `/privacy-policy` и `/data-deletion`; обе вернули HTTP 200, а защищённый
`/api/accounts` без ключа — 401. Root pnpm check перед этой публикацией прошёл.
Повторная read-only проверка production подтвердила 239 объектов без усечения.

Контрольный запрос 2026-10-03 06:16 UTC к media `18008882497265003` тем же
подключённым токеном и `fields=id,text,timestamp`, `limit=50` по-прежнему вернул
comments_count=270 и шесть пустых страниц. Field expansion `comments` отсутствует
в ответе объекта, а `summary=true` не даёт total_count. Публикация информационных
страниц сама по себе не меняет режим приложения Meta.

Для проверки режима требовалось завершить настройку в существующем кабинете
Meta, затем повторить этот же запрос и полный сбор. Управление Chrome вернуло
Apple Events −1743; системный журнал macOS связал отказ с недоступным временным
путём Chrome `code_sign_clone`, несмотря на включённое разрешение автоматизации.
Пользователю предложен перезапуск Chrome. Это отдельный сбой доступа к кабинету,
а не доказательство причины пустых комментариев в API. Диагностика продолжается.

Последние Reels от 2026-09-30, 2026-09-29 и 2026-09-25 имеют
is_comment_enabled=true и comments_count 8, 8 и 17 соответственно; их
comments edge также возвращает HTTP 200 и data=[]. Выключенные комментарии
на этих публикациях не объясняют пустые ответы.

В Sites 10 опубликован адаптер 0.3.4: в описаниях MCP compare_media и
get_account_summary тоже удалены прежние ограничения 100/1000 объектов.
Реальные значения выборки уже были полными в backend; теперь согласованы
описания инструментов и документация. Root pnpm check прошёл (70 тестов),
22 read-only MCP-инструмента проверены против production 0.2.6. Проверка
периодов выбирает сохранённые равные интервалы, а не предполагает, что при
смене даты уже были собраны новые интервалы. Доступ Sites остаётся приватным
для одного владельца.

Диагностика доступа к кабинету: системный Accessibility разрешён для текущего
процесса, но при заблокированном Mac Chrome возвращал 0 доступных окон.
После разблокировки нативный Accessibility позволил прочитать и настроить
существующее приложение Meta, несмотря на сохраняющийся Apple Events −1743.
Прежний диагностический onConsole=false был результатом ошибочного имени ключа:
реальный kCGSSessionOnConsoleKey=true. Это исправлено; отсутствие консольной
сессии не считается установленной причиной системного отказа.

Для постоянного сбора исправлена скорость фонового прохода: вместо одной
страницы задания каждые 15 минут Cron работает каждые 5 минут и продвигает
до двенадцати страниц, с максимум одной страницей прочих заданий. Отдельная операция
расписания сохраняет сбор активности и обновление публикаций. Lease и backoff
соблюдаются между страницами; занятому заданию дают продолжить другие задания.
Root pnpm check: 56 backend и 17 MCP/UI тестов прошли, включая ограничение
бюджета, обслуживание расписания, backoff/resume и чужой lease.
